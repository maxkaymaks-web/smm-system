# SMM-система bit&pix — Codex project entry point

Файл загружается автоматически Codex при `cd smm-system && codex`.
Основной режим: оператор запускает `codex` руками из репозитория и работает
с ним как с сильным помощником. **1 задача = 1 сессия.** По окончании сессии
оператор фиксирует важные решения в `projects/<ProjectID>/session-log.md`.

> Видение и процесс зафиксированы: интервью начальника — `docs/onboarding-process.md`,
> целевая архитектура и план — `docs/superpowers/specs/2026-06-12-notion-gdrive-integration-design.md`.
> Где что хранится **сейчас vs цель** — `docs/storage.md`.

## Новая модель работы (коротко)

Раньше посты генерировались автономными агентами (через OpenClaw-бота в
Telegram). **Это отключено.** Теперь:

- **Оператор ведёт много проектов параллельно** — сам делает посты, заполняет
  контентом, держит окна задач. Таких операторов несколько.
- **Codex (ты) = сильный помощник.** Знаешь типовые решения агентства:
  как пишем посты, как верстаем, как разбираем ОС, как поступаем в разных
  ситуациях. Помогаешь оператору, а не делаешь всё за него автономно.
- **Агенты-эксперты** (`copywriter`, `designer`, `analytics`, `brief`,
  `content-planner`, `dushnila`) — нативные сабагенты Codex в
  `.codex/agents/<name>.md`. Зови их через Agent tool, когда это ускоряет
  работу. Это **не обязаловка**: оператор может работать и напрямую с тобой.
- **Финальную публикацию всегда жмёт человек.** Нейросеть сама в соцсети ничего
  не публикует.

### Два окна + Notion за ними

- **Chatwoot** — клиентские диалоги, омниканал TG/VK/MAX. Развёрнут.
- **Codex (ты)** — основной рабочий экран: подсказываешь что следующим,
  вместе с оператором делаешь пост, ведёшь Notion. Готовый пост оператор
  **публикует руками** в соцсети.
- **Публикация — вручную.** Автопостинг (Postiz) пробовали — не интегрировали,
  отказались. Оператор постит сам; автопостинг — кандидат в кабинет (smm-app, позже).
- **Notion** — БД/источник истины операционки (базы «Клиенты»/«Планы»/«Посты»)
  + Kanban для начальника. Ведёшь ты; начальник смотрит/иногда правит.

## При каждом запуске — читать в этом порядке

0. **ВСЕГДА в начале сессии подтянуть обновления из репозитория.** Проверь, есть
   ли свежие коммиты на `origin/main`, и если есть — подтяни их, прежде чем
   читать что-либо ниже (чтобы работать на актуальной версии системы):
   ```bash
   git fetch origin
   git log --oneline HEAD..origin/main   # если пусто — обновлений нет
   git pull --ff-only origin main        # подтянуть, если рабочее дерево чистое
   ```
   Если рабочее дерево грязное (есть незакоммиченные правки) или `--ff-only` не
   проходит — не делай force/merge молча, сообщи оператору и спроси, как поступить.
1. `global/UPDATES.md` — свежие изменения системы (самые новые сверху)
2. `global/rules.md` — общие правила работы (включая YAGNI)
3. `global/memory/MEMORY.md` — **память оператора** (общая, в git): повторяющиеся
   грабли платформ и «так у нас принято». Это **замена личной памяти Codex** —
   per-machine память харнесса в этом репо выключена (`.codex/settings.json` →
   `autoMemoryEnabled: false`), т.к. не шарилась между операторами и терялась.
   Релевантна тема — дочитай нужный файл из `global/memory/` целиком.
   **Только в dev/`_unscoped`-сессиях** дополнительно читай `global/dev-memory/MEMORY.md`
   (инфра/серверы/внутренняя кухня) — в обычной операторской сессии она не нужна.
4. Спросить у оператора: с каким проектом работаем + что делаем
5. `projects/{ProjectID}/voice.md` + `context.md` + `overrides.md` +
   `session-log.md` — голос, контекст, **накопленный свод правил клиента**
   (секция «Накопленные правила» в `overrides.md` — как клиент любит, выросло из
   прошлых правок; см. правило «Фиксация правок клиента» в `global/rules.md`) и
   **журнал прошлых сессий** (`session-log.md` — 1 строка на сессию: что делали /
   что решили на будущее; это НЕ очередь постов — очередь в Notion)
6. **Если задача про посты** («сделай следующий пост», «что дальше», работа с
   `posts/`) — **до работы** прочитать очередь из Notion (база «Посты» по
   клиенту, сортировка по `Дедлайн`) и показать оператору: очередь + статусы +
   явно «следующий = X». Codex не помнит очередь между сессиями - он её читает.
   Инструмент — скилл `ежедневный-брифинг`. Подробно — `global/rules.md` →
   «Очередь постов и статусы в Notion».

## Архитектура

```
оператор + Codex (codex в этом репо)
  ├─ при необходимости зовёт сабагентов-экспертов через Agent tool:
  │   copywriter, designer, analytics, brief, content-planner, dushnila
  │   (.codex/agents/<name>.md)

  ├─ ведёт   → Notion: базы «Клиенты»/«Планы»/«Посты» (операционка, источник истины)
  ├─ пишет   → projects/{ProjectID}/posts/drafts/{дата}-{N}/ (рабочие черновики)
  ├─ отдаёт  → готовый пост оператору → оператор публикует РУКАМИ в соцсети

Генерация изображений / видео / TTS
  └─→ fal.ai напрямую (без прокси).

Хранилища (подробно — docs/storage.md):
  • Операционка (статусы, план, задачи)  → Notion (источник истины)
  • Знания клиента (context/voice/strategy/overrides) + ноу-хау → git
  • Медиа (HTML/PNG/JPG/PDF/MP4)          → S3 Timeweb, бакет seo, префикс smm/
                                            (Google Drive рассматривали — отказались)
  Локально файлы — временные в /tmp.

Диалоги с клиентом   → Chatwoot (TG/VK/MAX).
Публикация           → вручную (оператор постит сам; автопостинг не интегрирован).
```

## Тренды

Канал `@bitandpix_reels` - видеотренды для авторов контента. Полный порядок
(разбор видео, шаблон поста, требования к файлам, коды ошибок) -
`docs/trends.md`. Коротко:

- **Сначала кабинет, потом канал.** Тренд заливается в `app.bitandpix.ru`
  (`POST /api/v1/trends`, ключ из защищенной конфигурации в заголовке
  `X-Trends-Upload-Key`), в ответ приходит
  номер `BPT021` - он и печатается в посте. Номера выдаёт кабинет: вести их
  руками больше не нужно, старый реестр `bitandpix-trends/trends/index.md`
  разъехался с каналом и не используется.
- **Тип тренда обязателен:** `trend`, `microtrend` или `meme`. Без него не
  примут.
- **Примеры пишутся тремя частями** (что в начале видео, что после склейки,
  какой эффект): из них кабинет собирает клиенту сценарий по тренду.
- **Видео - только mp4/H.264 до 60 секунд**, айфоновский `.MOV` перегоняется
  ffmpeg. Исходником может быть картинка (JPEG/PNG), мем-нарезка - всегда видео.
- **Публикует человек.** Пост не выкладывается, пока тренд не принят кабинетом:
  иначе в канале окажется номер, которого у нас нет.

## Git

После изменения файлов проекта — предложи закоммитить и запушить, но
**сначала спроси подтверждение оператора**. Не коммить и не пушь автоматически.
Подтверждение спрашивается один раз на пару коммит+пуш: **если коммит сделан, сразу за
ним идёт `git push origin main`** — коммит без пуша не оставляем.

```bash
git add .
git commit -m "<scope>: <action> — <ProjectID>"
git push origin main
```

Скоупы: `posts`, `content-plan`, `analytics`, `brief`, `designer`, `agents`, `tools`, `docs`, `feedback`, `memory`.

## Правила

- Не редактировать `voice.md` без явной команды оператора
- **«Запомни / запиши / на будущее» → всегда в конкретный файл репо, и назови путь.**
  Правка/предпочтение клиента → `projects/{ProjectID}/overrides.md` (секция
  «Накопленные правила») или `feedback/`; операторский факт → `global/memory/`;
  инфра/системный факт (только dev-сессии) → `global/dev-memory/`. Личная память
  Codex в этом репо выключена и для сохранений запрещена. После сохранения скажи
  оператору: «Зафиксировал в `<точный путь>`: <что>». Без названного пути в репо —
  это баг. (Полное правило — `global/rules.md` → «Фиксация правок клиента».)
- **Сервер — зона разработчика.** SSH, деплой, правка сервисов на сервере, доступы —
  делает только разработчик. Оператор на сервер не лезет и команды на нём не гоняет;
  если что-то лежит в инфраструктуре или нужен доступ — пинг разработчику
  (Максим / Pavel), не чинить самому.
- Коммит и пуш разрешены, но **каждый раз спрашивать подтверждение оператора**
  перед `git commit` и `git push` (не автоматически). Разрешение даётся сразу на пару:
  сделал коммит - сразу `git push origin main`, коммит без пуша не оставляем
- Не добавлять в коммиты служебные подписи ассистента (`Co-Authored-By`, `Generated with ...`).
- Секреты — только в `.env`. Не-секретные константы (ID баз Notion и т.п.) —
  открыто в репо (`config/notion.json`)
- YAGNI: не плодить «на всякий случай», не оставлять обратной совместимости после миграции (см. `global/rules.md`)

## Сабагенты и ресёрч

- **Гуглить/искать документацию — через сабагентов**, но ТОЛЬКО типом `Explore`: у него в
  наборе всё, кроме `Agent`, поэтому он физически не может наспавнить своих подагентов.
  Тип `general-purpose` для ресёрча НЕ использовать: у него тулы `*`, включая `Agent`, и на
  широкий промпт он разворачивает веер на десятки агентов.
- **Промпт ресёрча узкий:** не больше 3-4 кандидатов/вопросов за вызов. Список из 12
  пунктов агент читает как приглашение распараллелить по пункту на агента.
- **Одновременно не больше 7 ресёрч-агентов.** Нужно больше - спросить разрешение.
- **`Workflow` (мультиагентная оркестрация) не запускать без явной просьбы пользователя** -
  он рассчитан на десятки агентов и сжигает бюджет.
- **Артефакты - через файлы, а не через контекст.** Всё, что сабагент печатает в ответ,
  оседает в основном контексте до конца сессии и перечитывается на каждом ходу. Поэтому в
  промпте агента требовать: полный результат (отчёт, найденные места в коде, список файлов)
  писать в `tmp/`, возвращать путь + резюме до ~5 строк. Простыня текста в ответе агента -
  это баг промпта, а не норма. То же про собственное чтение: `Read` с `offset`/`limit` по
  нужному фрагменту вместо файла целиком, и не перечитывать уже прочитанное.
- **Playwright MCP - параллельно с другими сессиями.** Сервер Playwright стартует на
  каждую сессию Codex. Без `--isolated` профиль браузера один на каталог проекта
  (`~/.cache/ms-playwright-mcp/mcp-chrome-<хеш пути>`), и вторая сессия в том же проекте
  падает на "Browser is already in use". Поэтому в `~/.codex/settings.json` в `env`
  стоит `PLAYWRIGHT_MCP_ISOLATED=true`: профиль у каждой сессии в памяти, и сессии любых
  проектов открывают браузер одновременно. Переменную не снимать, свой playwright-сервер
  без `--isolated` не прописывать. Видишь "Browser is already in use" - сессия стартовала
  раньше, чем появилась переменная: попроси пользователя перезапустить сессию, а чужие
  процессы chrome/playwright не трогай, это браузер другого агента. Внутри одной сессии
  браузер один на всех сабагентов, поэтому Playwright-сабагенты одной сессии идут по
  очереди, не параллельно. Логин в профиле в памяти не переживает сессию: входить заново
  в начале прогона.

## Русский текст

Действует, когда пишешь русский текст, который прочитает человек: строки интерфейса,
сообщения об ошибках, документацию, промпты, письма, посты. Не действует на код,
идентификаторы и коммиты.

Инструкция "пиши живее" не работает - это проверено замерами, эффект нулевой. Ниже
только то, что можно проверить глазами в готовом тексте.

### Зачины и концовки

- Не начинать с пустого: "в современном мире", "давайте разберёмся", "важно понимать,
  что", "стоит отметить", "не секрет, что", "итак". Начинай с сути.
- Не заканчивать служебным: "таким образом", "подводя итог", "в заключение". Останавливайся
  на последней содержательной мысли.
- Вырезать реплики ассистента: "отличный вопрос", "надеюсь, это помогло", "сейчас всё объясню".
- Не обещать качество вперёд текста: "коротко и по делу", "без воды", "разложу по полочкам",
  "скажу честно". Если текст короткий и честный, это видно и так.

### Структура - это важнее списков слов

- Длина предложений разная. Три подряд одинаковых - переписать одно.
- Не рубить на односоставные: "Коротко. Точно. По делу." Это такой же машинный тик, как
  канцелярит, просто новее. Связывай мысли союзами и придаточными.
- Не группировать по три ("быстро, надёжно и удобно"). Пунктов столько, сколько их есть.
- Не завершать каждый абзац выводом. Часть мыслей оставляй без бантика.
- Списки - только когда перечисление действительно списочное. Мысль, которая помещается
  в предложение, не становится яснее от буллетов.

### Ложная антитеза - главный маркер

Конструкции "не X, а Y", "это не просто X, это Y", "дело не в X, а в Y", "не только X,
но и Y" запрещены, когда X никто не утверждал. Пиши сразу Y.

- "Это не баг, а фича" -> "Так и задумано".
- "Это не просто инструмент, а целая экосистема" -> "Тут редактор, отладчик и пакетный менеджер".
- "Дело не в модели, а в промпте" -> "Всё решает промпт".

Исключение: оба полюса несут факт. "Выросло не на 2%, а на 40%" - нормально.

### Канцелярит

- "является" -> тире или перестроить предложение. "осуществлять" -> делать.
  "в настоящее время" -> сейчас. "данный" -> этот.
- Отглагольные существительные разворачивать в глагол: "осуществление проверки" -> "проверить",
  "обеспечение возможности доступа" -> "позволяет войти".
- Цепочка родительных падежей от трёх подряд - перестроить: "улучшение качества обслуживания
  клиентов" -> "клиентов станут лучше обслуживать".
- Пассив без нужды: "было принято решение" -> "мы решили", "работа выполняется" -> "команда делает".

### Конкретика вместо обобщения

Модель по умолчанию сглаживает факт до обобщения. Это надо ловить и возвращать назад.

- "столкнулись с финансовыми трудностями" -> "потеряли 400 тысяч на кампании".
- Оценки без доказательства - "качественный", "надёжный", "эффективный", "уникальный",
  "оптимальный" - заменять на свойство, число или срок.
- Фантомная атрибуция запрещена: "исследования показывают", "эксперты считают", "принято
  считать". Либо имя и ссылка, либо утверждения нет.
- Выхолощенность: "зависит от ряда факторов", "имеет свои особенности", "играет важную роль".
  Назови факторы, особенности и роль или убери фразу.

### Чего не делать, когда правишь

- Не стерилизовать. Убрать штамп и убрать голос - разные вещи; правка должна звучать
  как тот же автор.
- Не менять один штамп на другой. Выкинул "таким образом" - не начинай теперь всё
  с "при этом".
- Живость не изображается эмодзи, восклицательными знаками, псевдовопросами ("Зачем?
  Затем.") и панибратством. Живым текст делают детали, а не украшения.
- Длинное тире не ставить вообще. Двоеточие, скобки, точка, дефис.

### Проверка перед сдачей

1. Прочитать вслух. Где спотыкаешься - там и правь.
2. Найти самое общее утверждение в тексте и заменить его фактом.
3. Посмотреть на длины предложений подряд. Если они ровные - сломать ритм.

## SSH

На серверах пользователя SSH-порт зачастую 24822, а не 22. Использовать `-p 24822` если стандартный порт не отвечает.

## Сеть / VPN

Рабочая машина выходит в интернет через VPN (Koala Clash, Cloudflare WARP и др.),
поэтому публичный IP **динамический и часто меняется** (пользователь регулярно
переключает VPN). НЕ завязывать доступы на конкретный IP рабочей машины (ufw allow,
fail2ban ignore, proxy allow-list по IP): к серверным ресурсам с IP-ограничением
(egress-прокси и т.п.) обращаться **с самого сервера по SSH**, а не с рабочей машины.
