# SMM-система bit&pix — Claude Code entry point

Файл загружается автоматически Claude Code при `cd smm-system && claude`.
Основной режим: оператор запускает `claude` руками из репозитория и работает
с ним как с сильным помощником. **1 задача = 1 сессия.** По окончании сессии
(с подтверждения оператора) транскрипт + саммари выгружаются в архив
(`docs/session-finalize.md`).

> Видение и процесс зафиксированы: интервью начальника — `docs/onboarding-process.md`,
> целевая архитектура и план — `docs/superpowers/specs/2026-06-12-notion-gdrive-integration-design.md`.
> Где что хранится **сейчас vs цель** — `docs/storage.md`.

---

## Новая модель работы (коротко)

Раньше посты генерировались автономными агентами (через OpenClaw-бота в
Telegram). **Это отключено.** Теперь:

- **Оператор ведёт много проектов параллельно** — сам делает посты, заполняет
  контентом, держит окна задач. Таких операторов несколько.
- **Claude Code (ты) = сильный помощник.** Знаешь типовые решения агентства:
  как пишем посты, как верстаем, как разбираем ОС, как поступаем в разных
  ситуациях. Помогаешь оператору, а не делаешь всё за него автономно.
- **Агенты-эксперты** (`copywriter`, `designer`, `analytics`, `brief`,
  `content-planner`, `dushnila`) — нативные сабагенты Claude Code в
  `.claude/agents/<name>.md`. Зови их через Agent tool, когда это ускоряет
  работу. Это **не обязаловка**: оператор может работать и напрямую с тобой.
- **Финальную публикацию всегда жмёт человек.** Нейросеть сама в соцсети ничего
  не публикует.

### Два окна + Notion за ними

- **Chatwoot** — клиентские диалоги, омниканал TG/VK/MAX. Развёрнут.
- **Claude Code (ты)** — основной рабочий экран: подсказываешь что следующим,
  вместе с оператором делаешь пост, ведёшь Notion. Готовый пост оператор
  **публикует руками** в соцсети.
- **Публикация — вручную.** Автопостинг (Postiz) пробовали — не интегрировали,
  отказались. Оператор постит сам; автопостинг — кандидат в кабинет (smm-app, позже).
- **Notion** — БД/источник истины операционки (базы «Клиенты»/«Планы»/«Посты»)
  + Kanban для начальника. Ведёшь ты; начальник смотрит/иногда правит.

## При каждом запуске — читать в этом порядке

0. **ВСЕГДА в начале сессии подтянуть обновления из репозитория.** Проверь, есть
   ли свежие коммиты на `origin/main`, и если есть — подтяни их, прежде чем
   читать что-либо ниже (чтобы работать на актуальной версии системы):
   ```bash
   git fetch origin
   git log --oneline HEAD..origin/main   # если пусто — обновлений нет
   git pull --ff-only origin main        # подтянуть, если рабочее дерево чистое
   ```
   Если рабочее дерево грязное (есть незакоммиченные правки) или `--ff-only` не
   проходит — не делай force/merge молча, сообщи оператору и спроси, как поступить.
1. `global/UPDATES.md` — свежие изменения системы (самые новые сверху)
2. `global/rules.md` — общие правила работы (включая YAGNI)
3. `global/memory/MEMORY.md` — **память оператора** (общая, в git): повторяющиеся
   грабли платформ и «так у нас принято». Это **замена личной памяти Claude** —
   per-machine память харнесса в этом репо выключена (`.claude/settings.json` →
   `autoMemoryEnabled: false`), т.к. не шарилась между операторами и терялась.
   Релевантна тема — дочитай нужный файл из `global/memory/` целиком.
   **Только в dev/`_unscoped`-сессиях** дополнительно читай `global/dev-memory/MEMORY.md`
   (инфра/серверы/внутренняя кухня) — в обычной операторской сессии она не нужна.
4. Спросить у оператора: с каким проектом работаем + что делаем
5. `projects/{ProjectID}/voice.md` + `context.md` + `overrides.md` +
   `session-log.md` — голос, контекст, **накопленный свод правил клиента**
   (секция «Накопленные правила» в `overrides.md` — как клиент любит, выросло из
   прошлых правок; см. правило «Фиксация правок клиента» в `global/rules.md`) и
   **журнал прошлых сессий** (`session-log.md` — 1 строка на сессию: что делали /
   что решили на будущее; это НЕ очередь постов — очередь в Notion)
6. **Если задача про посты** («сделай следующий пост», «что дальше», работа с
   `posts/`) — **до работы** прочитать очередь из Notion (база «Посты» по
   клиенту, сортировка по `Дедлайн`) и показать оператору: очередь + статусы +
   явно «следующий = X». Клод не помнит очередь между сессиями — он её читает.
   Инструмент — скилл `ежедневный-брифинг`. Подробно — `global/rules.md` →
   «Очередь постов и статусы в Notion».

## При завершении сессии — финализация

> **Железное правило логирования: тронул `projects/<клиент>/` — сессию ОБЯЗАН залогировать.**
> Если за сессию ты читал или писал что-либо под `projects/<ID>/` (любой клиент,
> кроме `_template` и `_unscoped`) — это клиентская работа, и она обязана уехать в
> архив через финализацию. Это **не «предложи, если вспомнишь», а обязательство**:
> не закрывай сессию, пока не финализировал — или пока оператор явно не сказал
> «эту не логируем».
> Сессия, которая не касалась ни одной папки `projects/<клиент>/` (dev, инфра,
> `_unscoped`, разбор самой системы) — логировать **НЕ требуется**, не навязывай.

**Claude обязан сам инициировать финализацию — не ждать, пока оператор вспомнит.**
Как только задача (или законченный кусок работы по клиенту) выглядит сделанной —
сам спроси: **«Задачу закрываем? Выгружаю логи сессии в S3?»**. Логи копятся
локально и теряются для архива, если их не выгрузить — раньше так и проебали
3 недели сессий. Поэтому спрашивать — обязательно, каждый раз.

Триггеры, на которых ОБЯЗАН задать этот вопрос (даже если оператор не сказал
«финализируй»):
- оператор написал «всё ок / готово / спасибо / закрываемся / финализируй»
  / `/finalize` или семантически близкое;
- пост согласован/выдан, контент-план готов, аналитика отдана — задача закрыта;
- оператор явно сворачивается («на сегодня всё», «пойду»).

Когда подтвердил — прочитай **`docs/session-finalize.md`** и выполни процедуру:
напиши `summary.md` по шаблону, запусти
`node tools/upload-session.mjs <ProjectID> --summary ...`.

Перед финализацией **обязательно опроси оператора**:
- «Точно всё сделали по задаче?»
- «Делал что-то вне Claude Code (руками, в другом окне)? Опиши — зафиксирую
  в саммари.» — это важно, чтобы лог сессии был полным для последующего
  анализа паттернов «что сработало / что нет».

**Исключение — dev/инфра-сессии разработчика** (`ProjectID = _unscoped`: правка
тулзов, доков, разбор багов системы). Это работа над самой системой, а не
оператора с клиентом — НЕ навязывай выгрузку. Можешь один раз мягко предложить;
сказали «не надо» — не настаивай.

Цель — накопить корпус **клиентских** сессий (JSONL + meta + summary), который
потом раз в неделю/месяц анализируется: хорошие паттерны выносятся в
документацию, плохие — в стоп-лист.

## Что это за проект

SMM-агентство bit&pix. Помогаешь оператору делать:
- Контент-планы (ведутся в Notion; клиенту уходит PDF-снапшот)
- Тексты постов и адаптации под VK/MAX/Instagram/Telegram
- HTML-макеты слайдов и каруселей + fal.ai-генерация ассетов
- Анализ конкурентов через Apify/VK API
- Обработку фидбека от заказчика
- Создание новых проектов через диалог-бриф (см. `docs/client-onboarding.md`)

Под капотом — Claude через подписку Claude Code (Anthropic),
fal.ai (картинки/видео), Apify (парсинг).

## Архитектура

```
оператор + Claude Code (claude в этом репо)
  ├─ при необходимости зовёт сабагентов-экспертов через Agent tool:
  │   copywriter, designer, analytics, brief, content-planner, dushnila
  │   (.claude/agents/<name>.md)
  ├─ читает  → projects/{ProjectID}/{context,voice,strategy,overrides}.md  (git)
  ├─ ведёт   → Notion: базы «Клиенты»/«Планы»/«Посты» (операционка, источник истины)
  ├─ пишет   → projects/{ProjectID}/posts/drafts/{дата}-{N}/ (рабочие черновики)
  ├─ отдаёт  → готовый пост оператору → оператор публикует РУКАМИ в соцсети
  └─ в конце → upload-session.mjs → архив сессий (см. docs/session-finalize.md)

Генерация изображений / видео / TTS
  └─→ fal.ai напрямую (без прокси).

Хранилища (подробно — docs/storage.md):
  • Операционка (статусы, план, задачи)  → Notion (источник истины)
  • Знания клиента (context/voice/strategy/overrides) + ноу-хау → git
  • Медиа (HTML/PNG/JPG/PDF/MP4)          → S3 Timeweb, бакет seo, префикс smm/
                                            (Google Drive рассматривали — отказались)
  • Архив сессий Claude Code              → S3 (logs/claude-code/…)
  Локально файлы — временные в /tmp.

Диалоги с клиентом   → Chatwoot (TG/VK/MAX).
Публикация           → вручную (оператор постит сам; автопостинг не интегрирован).
```

| Статус | Значение |
|--------|----------|
| `черновик` | Не начат |

## Git

После изменения файлов проекта — предложи закоммитить и запушить, но
**сначала спроси подтверждение оператора**. Не коммить и не пушь автоматически.

```bash
git add .
git commit -m "<scope>: <action> — <ProjectID>"
git push origin main
```

Скоупы: `posts`, `content-plan`, `analytics`, `brief`, `designer`, `agents`, `tools`, `docs`, `feedback`, `memory`.

## Правила

- Не редактировать `voice.md` без явной команды оператора
- **«Запомни / запиши / на будущее» → всегда в конкретный файл репо, и назови путь.**
  Правка/предпочтение клиента → `projects/{ProjectID}/overrides.md` (секция
  «Накопленные правила») или `feedback/`; операторский факт → `global/memory/`;
  инфра/системный факт (только dev-сессии) → `global/dev-memory/`. Личная память
  Claude в этом репо выключена и для сохранений запрещена. После сохранения скажи
  оператору: «Зафиксировал в `<точный путь>`: <что>». Без названного пути в репо —
  это баг. (Полное правило — `global/rules.md` → «Фиксация правок клиента».)
- **Сервер — зона разработчика.** SSH, деплой, правка сервисов на сервере, доступы —
  делает только разработчик. Оператор на сервер не лезет и команды на нём не гоняет;
  если что-то лежит в инфраструктуре или нужен доступ — пинг разработчику
  (Максим / Pavel), не чинить самому.
- Коммит и пуш разрешены, но **каждый раз спрашивать подтверждение оператора**
  перед `git commit` и `git push` (не автоматически)
- **В сообщениях коммитов не упоминать Claude:** ни `Co-Authored-By: Claude`, ни
  "Generated with Claude Code", ни любое другое упоминание ассистента - ни в теме, ни в
  теле, ни трейлером. Действует всегда, в том числе там, где коммитить агенту нельзя, а
  коммит делается по прямой просьбе пользователя.
- Секреты — только в `.env`. Не-секретные константы (ID баз Notion и т.п.) —
  открыто в репо (`config/notion.json`)
- YAGNI: не плодить «на всякий случай», не оставлять обратной совместимости после миграции (см. `global/rules.md`)

## Сабагенты и ресёрч

- **Гуглить/искать документацию — через сабагентов**, но ТОЛЬКО типом `Explore`: у него в
  наборе всё, кроме `Agent`, поэтому он физически не может наспавнить своих подагентов.
  Тип `general-purpose` для ресёрча НЕ использовать: у него тулы `*`, включая `Agent`, и на
  широкий промпт он разворачивает веер на десятки агентов.
- **Промпт ресёрча узкий:** не больше 3-4 кандидатов/вопросов за вызов. Список из 12
  пунктов агент читает как приглашение распараллелить по пункту на агента.
- **Одновременно не больше 7 ресёрч-агентов.** Нужно больше - спросить разрешение.
- **`Workflow` (мультиагентная оркестрация) не запускать без явной просьбы пользователя** -
  он рассчитан на десятки агентов и сжигает бюджет.
- **Артефакты - через файлы, а не через контекст.** Всё, что сабагент печатает в ответ,
  оседает в основном контексте до конца сессии и перечитывается на каждом ходу. Поэтому в
  промпте агента требовать: полный результат (отчёт, найденные места в коде, список файлов)
  писать в `tmp/`, возвращать путь + резюме до ~5 строк. Простыня текста в ответе агента -
  это баг промпта, а не норма. То же про собственное чтение: `Read` с `offset`/`limit` по
  нужному фрагменту вместо файла целиком, и не перечитывать уже прочитанное.
