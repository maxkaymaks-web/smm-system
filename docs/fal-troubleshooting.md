# fal.ai не работает / `ECONNRESET` под VPN — диагностика и лечение

> TL;DR для оператора под VPN: добавь в `.env` строку
> `FAL_PROXY=http://127.0.0.1:10809` (адрес локального прокси твоего VPN-клиента)
> — и перезапусти задачу. Тулзы пустят fal.ai через прокси и перестанут падать.

---

## Симптом

`generate-image` / `analyze-image` / `remove-bg` и т.п. падают с `ECONNRESET`
(`socket hang up`, `fetch failed`, `terminated`), особенно на «крупных» запросах
(генерация/аплоад картинки). Баланс fal.ai при этом пополнен — **дело не в деньгах
и не в промпте, а в сети.**

## Почему так

1. Операторы сидят под VPN, чтобы зарубежные сервисы (fal.ai, OpenAI, Anthropic)
   вообще были доступны — **из РФ напрямую fal.ai режется.**
2. VPN-клиент (v2rayN / Nekoray / Clash и т.п.) поднимает локальный прокси,
   обычно `127.0.0.1:10809` (HTTP) или `:10808` (SOCKS).
3. Node-овский `fetch` (на нём работает `@fal-ai/client`) **НЕ читает**
   `HTTPS_PROXY`/`ALL_PROXY` из окружения сам по себе. Поэтому запрос уходит
   мимо прокси → напрямую → РФ-блокировка рвёт соединение → `ECONNRESET`.

Это тот же класс проблемы, что описан в памяти проекта: «fetch ≠ env-прокси →
нужен ProxyAgent».

## Лечение (рекомендуемое) — `FAL_PROXY` в `.env`

1. Узнай адрес локального прокси своего VPN-клиента (в v2rayN — это «http proxy
   port», обычно `10809`; в настройках клиента видно порт).
2. В корне репозитория в `.env` добавь строку:
   ```
   FAL_PROXY=http://127.0.0.1:10809
   ```
   (если у клиента только SOCKS — `FAL_PROXY=socks5://127.0.0.1:10808`)
3. Перезапусти задачу/генерацию. В stderr появится `[net-proxy] fal.ai через
   прокси http://127.0.0.1:10809` — значит трафик пошёл через прокси.

Под капотом тулзы поднимают `undici ProxyAgent` и ставят его глобальным
диспетчером для `fetch` (`tools/lib/net-proxy.mjs`, подключён через
`tools/lib/fal-meter.mjs`). Плюс fal-вызовы теперь **ретраятся 3 раза** на
сетевых обрывах (`TIMEOUT` не ретраится — это осознанно).

## Альтернатива без `.env` — TUN/Global режим VPN

Если в VPN-клиенте включить **TUN mode / «Режим Tun» / Global**, весь TCP-трафик
(включая Node) пойдёт через туннель прозрачно, мимо HTTP-прокси — `FAL_PROXY`
тогда не нужен. Минус: туннелит вообще всё, иногда нестабильнее на больших
аплоадах. Если выбрал этот путь — `FAL_PROXY` из `.env` убери.

## Быстрая диагностика

```bash
# 1. Есть ли вообще связь с fal (через прокси, если он у тебя на 10809):
curl -s -o /dev/null -w "fal.run -> HTTP %{http_code} | %{time_total}s\n" \
  --max-time 15 -x http://127.0.0.1:10809 https://fal.run/
#   HTTP 404 = достучались (это норма для корня). Таймаут/0 = прокси не тот / VPN не поднят.

# 2. Тот же запрос без -x (напрямую) — если из РФ висит/рвётся, значит нужен прокси:
curl -s -o /dev/null -w "напрямую -> HTTP %{http_code}\n" --max-time 15 https://fal.run/
```

- Через `-x` отвечает, а напрямую нет → классика, ставь `FAL_PROXY`.
- Не отвечает даже через `-x` → VPN/прокси не работает или порт другой, сначала
  почини сам VPN-клиент.

## Чего НЕ делать

- Не переформулировать промпт и не «пробовать другую модель» — это сетевая
  ошибка, к контенту отношения не имеет.
- Не пихать токен/прокси в код тулз руками — всё через `.env` (`FAL_PROXY`,
  `FAL_KEY`).
- Не путать с `TIMEOUT after N s` — это уже «fal.ai перегружен», не сеть; такое
  не ретраится, нужно просто сообщить оператору и подождать.
