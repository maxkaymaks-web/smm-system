# Финализация сессии Claude Code

Этот документ читает **сам Claude Code** в конце каждой задачи, когда оператор
подтвердил, что качество устраивает. Финализация = выгрузить транскрипт и
саммари в S3, чтобы накопить корпус для последующей автоматизации.

**Принцип:** 1 задача = 1 сессия. Сессия закрывается явно (оператор пишет
«всё, закрываемся» / «финализируй» / `/finalize` и т.п.). До этого момента
ничего не выгружается.

---

## Когда финализировать

Когда оператор сказал что-то из:
- «всё устраивает, закрываемся»
- «финализируй сессию»
- «сохрани и закрывайся»
- `/finalize`, `/wrap-up`
- любая семантически близкая формулировка

**Если оператор задачу не подтвердил** — не финализируй. Уточни: «Качество
устраивает? Готов финализировать?». Финализация = заморозка; продолжать
работу после неё нельзя в этой же сессии (точнее можно, но в S3 уйдёт версия
до — следующая финализация перезатрёт).

### Перед финализацией — опроси оператора

Лог сессии должен быть полным, иначе анализ паттернов «что сработало / что нет»
будет врать. Поэтому до записи саммари спроси:

1. **«Точно всё сделали по задаче?»** — вдруг остался незакрытый шаг.
2. **«Делал что-то вне Claude Code — руками, в другом окне, в браузере?»** Если
   да — попроси описать, и зафиксируй это в саммари (в `Recipe` отдельным шагом
   с пометкой «вне CC» или в `Decisions`). Без этого рецепт нельзя будет
   повторить: половина работы окажется невидимой в JSONL.

## Что делать — 4 шага

### Шаг 1. Определи `ProjectID`

Это **ID директории** в `projects/`. Смотри по контексту сессии:
- если читал `projects/Lakmoda/voice.md` → `Lakmoda`
- если рендерил `projects/Sparta/posts/...` → `Sparta`
- если несколько проектов — спроси оператора, какой основной
- если задача внепроектная (dev, инфра, разбор багов системы) → `_unscoped`

Не выдумывай новые ID. Список валидных — `ls projects/` (всё кроме `_template`).

### Шаг 2. Напиши саммари в `/tmp/session-summary.md`

Формат — **Hybrid**: машинно-читаемый frontmatter + подробный recipe-блок +
narrative с глубоким разбором ошибок. Шаблон ниже (см. раздел «Шаблон
summary.md»).

**Принципы:**

- **Пиши столько, сколько нужно.** Никаких «1-3 предложения», «коротко» и т.п. —
  будущий читатель не знает контекста, лучше избыток деталей, чем недосказанность.
  Если есть что добавить — добавляй.
- **Каждый шаг recipe — это конкретное действие с измеримым результатом.**
  Не «прочитал контекст», а «прочитал voice.md (1.2 KB, 28 строк), context.md
  (5.4 KB), content-plan.md — нашёл что 17.05 = пост-карусель, статус
  `черновик`». Чем конкретнее — тем легче автоматизировать.
- **Каждый вызванный tool — что подавал на вход и что получил.** Не просто
  «дал ТЗ копирайтеру», а полный текст ТЗ + размер ответа + конкретные правки
  если были. Не «запустил generate-image», а команда полностью + duration +
  ссылка на S3 / путь.
- **Ошибки — отдельный важный блок.** Любой неудачный tool_call, отказ модели,
  ретрай, замена подхода, фидбек оператора «нет, переделай» — фиксируй. Для
  каждого: что произошло, почему, как починил, **и (главное) какое правило/
  чек-лист добавить чтобы не повторить**. Это самая ценная часть саммари для
  будущей автоматизации — мы накапливаем не только «как делать», но и «какие
  грабли есть».
- **Заполняй честно.** Срезал угол → пиши. Нарушил правило → пиши. Спросил
  оператора там, где должен был сообразить сам → пиши. Цель — учиться, а не
  выставлять себя в выгодном свете.

Цель саммари: чтобы через месяц по нему можно было повторить ту же работу
руками (или скриптом), не читая 100 KB JSONL — и при этом обойти все грабли,
на которые наступили в этот раз.

### Шаг 3. Запусти uploader

```bash
node tools/upload-session.mjs <ProjectID> --summary /tmp/session-summary.md
```

Опции:
- `--session-id <UUID>` — если по какой-то причине нужно загрузить не последнюю
  сессию (default: берётся самый свежий `.jsonl` из
  `~/.claude/projects/-home-pavel-projects-smm-system/`)
- `--dry-run` — посмотреть meta без загрузки

Что произойдёт:
1. Парсится `~/.claude/projects/-home-pavel-projects-smm-system/{sid}.jsonl`
   → детерминистическая meta (usage, tool counts, файлы, bash-команды,
   subagents, первый prompt, длительность). Без LLM.
2. В S3 (`s3://seo/`) уходят 5 объектов:
   - `logs/claude-code/by-project/{ProjectID}/{YYYY-MM-DD}/{sid}/raw.jsonl`
   - `logs/claude-code/by-project/{ProjectID}/{YYYY-MM-DD}/{sid}/meta.json`
   - `logs/claude-code/by-project/{ProjectID}/{YYYY-MM-DD}/{sid}/summary.md`
   - `logs/claude-code/by-date/{YYYY}/{MM}/{DD}/{sid}.pointer.json`
   - `logs/claude-code/_index/all-sessions.jsonl` (обновляется)

Идемпотентно: повторный запуск перезапишет всё с тем же sid.

### Шаг 4. Подтверди оператору

После успешной загрузки покажи:
- S3-путь к саммари (`s3://seo/logs/claude-code/by-project/.../summary.md`)
- AI title и duration
- Что было сделано — 1-2 строки

Удалять `/tmp/session-summary.md` не обязательно.

## Recipe (шаги решения)

Нумерованный список **логических шагов** — 1 шаг = 1 осмысленное действие
(не каждый tool_call по отдельности, а законченный этап). Для каждого шага —
4 поля минимум: **Что делал / Почему / ТЗ или команда целиком / Результат** +
длительность если знаешь.

ТЗ агентам и команды Bash — **целиком в коде-блоке внутри шага**, без
`<details>` и без вынесения в отдельный файл. Полнота ТЗ — главная ценность
рецепта для будущей автоматизации.

## Lessons / разбор ошибок и инцидентов

Сюда — ВСЁ что пошло не идеально, даже если в итоге задача сделана. Под каждым
пунктом — подробный нарратив: **что произошло → почему так получилось → как
починил → как сделать чтобы не повторить (превенция)**.

Что фиксировать обязательно:

- **Tool fails** — любой `exit ≠ 0`, fetch failed, timeout, 4xx/5xx от API
- **Правки оператора** — любое «нет, переделай», «не так», «попробуй иначе»,
  даже если итог в итоге устроил
- **Отклонения от правил** — нарушил CLAUDE.md / rules.md / .claude/agents/*
  (например, попытался написать текст сам без copywriter; выбрал запрещённую
  модель; пушнул без подтверждения)
- **«Передумал»** — вызвал tool/агента X, получил результат, потом понял что
  нужен был Y; перечитал тот же файл дважды; пошёл не туда и вернулся

Пиши развёрнуто. Цель не отчёт «было — починил», а накопить грабли, на которые
не наступит ни следующая сессия, ни автоматизация поверх корпуса.

### 1. fal.ai вернул 502 при первой генерации слайда 1

Запустил `generate-image.mjs --model=nano-banana-2 ...` для первого слайда —
скрипт упал с exit 1, в stderr был `fal.ai 502 Bad Gateway`. Прокси tinyproxy
на `5.2.66.188:8888` периодически рвёт long-poll-соединение на этапе
`wait_for_completion` — это известный quirk fal-cli + tinyproxy (см. также
запись в [[no-direct-internet-from-ru-server]]).

**Как починил:** повторил тот же вызов без изменений, второй раз прошёл за
12 секунд. Слайды 2 и 3 сгенерировал с первой попытки.

**Как не повторить:**
1. В `tools/generate-image.mjs` добавить retry-логику на 502/504: 3 попытки с
   exponential backoff (2s → 4s → 8s). Сейчас её нет — каждый 502 это ручной
   ретрай.
2. В `global/rules.md` добавить явное правило: «первый 502 от fal.ai через
   tinyproxy = норма, повтори вызов без изменений; паниковать после 3
   подряд». Сейчас правило про лупы есть, но оно говорит «после двух
   одинаковых stop» — что прямо противоречит здравому подходу с fal.ai.
3. Долгосрочно — рассмотреть прямой HTTPS до fal.ai с RU-сервера через
   другой прокси (haproxy?), tinyproxy для длинных соединений плох.

### 2. Перечитал strategy.md дважды

В шаге 1 прочитал strategy.md чтобы взять CTA. В шаге 4, передавая ТЗ
designer'у, понял что не помню формулировку CTA дословно — и прочитал
strategy.md второй раз вместо того, чтобы посмотреть в свой же контекст.

**Почему:** не вынес ключевые данные из шага 1 в явный summary-блок в начале
работы. Контекст «расползся» по 40 turns, и проще оказалось повторить tool
call.

**Как не повторить:** после фазы сбора контекста (шаг 1) — явно фиксировать
в текстовом ответе «извлечённые ключи»: TOV в одну строку, табу-слова
списком, формат CTA для рубрики. Это и для оператора прозрачнее, и
страхует от повторных Read'ов через 20 шагов.

### 3. Оператор уточнил формат CTA на середине работы

После шага 3 (получил текст от copywriter) оператор написал: «CTA не такой —
не "запишитесь по ссылке", а "запись по ссылке в шапке профиля", у Lakmoda
теперь Instagram-приоритет». Перегенерил последний абзац.

**Почему:** не сверился с актуальным статусом проекта. В `context.md` было
указание про IG (новое после миграции с ВК), но в `strategy.md` ещё стояла
старая ВК-формулировка CTA — я взял из strategy без проверки на context.

**Как не повторить:**
1. Обновить `projects/Lakmoda/strategy.md` — синхронизировать CTA с context.md.
   Несоответствие обнаружено в этой сессии.
2. В правило «голос бренда» в CLAUDE.md добавить: «если в context.md и
   strategy.md противоречие — context.md приоритетнее, он свежее».
3. На уровне финализации этого summary — сделать TODO разработчику:
   проверить остальные проекты на такую же рассинхронизацию context vs
   strategy.

## Таксономия `task_type`

Выбирай ровно одно. Если не подходит ни одно — `other` + поясни в narrative.

`пост-фото-1`, `analytics-instagram`, ...). Не критично, для группировки.

## Поля frontmatter

| поле | значения | смысл |
|---|---|---|
| `project_id` | `Lakmoda` / `_unscoped` / ... | какой клиент (или `_unscoped` для общих задач) |
| `task_type` | из таблицы выше | категория задачи |
| `task_subtype` | свободный slug | подкатегория |
| `status` | `success` / `partial` / `failed` | реальный итог. `partial` = что-то сделал, что-то нет |
| `difficulty` | `trivial` / `easy` / `medium` / `hard` | твоя честная оценка |
| `automation_potential` | `none` / `low` / `medium` / `high` | насколько это можно зашить в скрипт без LLM |
| `reusable_recipe` | `true` / `false` | подходит ли этот рецепт для других проектов / других задач |
| `tags` | массив строк | произвольные метки для будущего поиска |

## Важные «не делай»

- **Не финализируй без явного подтверждения оператора.** Если оператор не
  сказал «закрываемся» — не выгружай.
- **Не выдумывай ProjectID.** Только из `ls projects/`.
- **Не сжимай саммари в одну фразу.** Цель — будущая автоматизация; деталь = валюта.
- **Не выгружай дважды подряд (без новых изменений).** Перезапись бессмысленна.
- **Не упоминай в саммари секреты.** `.env`, токены, ключи — никогда. Если в
  диалоге случайно мелькнул — упомяни «использовал ключ X из .env», без значения.
- **Не клади summary.md в git.** Он живёт только в `/tmp/` и в S3.
