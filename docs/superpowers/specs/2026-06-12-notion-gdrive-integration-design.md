# Интеграция Notion + Google Drive — дизайн

> Статус: дизайн согласован с разработчиком (Pavel), 2026-06-12. Реализация — отдельными
> фазами (см. «План реализации»). Источник решений — диалог в сессии, не интервью с
> начальником: по этим вопросам разработчик принял решение сам.

## Цель

Дать оператору голосовой интерфейс (он диктует → Claude Code исполняет) поверх трёх
хранилищ с чётким разделением ответственности. Минимум операционки на человеке —
максимум на Claude Code. Заменить S3-as-медиа на Google Drive, завести Notion как
операционный пульт (CRM), оставить базу знаний локально в git.

## Модель данных (Вариант А)

Правило размещения:

> **Часто меняется + человек смотрит глазами → Notion. Читаю как справку в начале
> задачи → локально (git). Бинарь → Drive. Машинный архив → S3.**

| Данные | Где живёт | Источник истины | Кто правит |
|--------|-----------|-----------------|------------|
| Планы постов, задачи-посты, статусы, очередь | **Notion** | Notion | Claude Code (я веду доску) |
| Тонкая карточка клиента (платформа, фокус, ссылка на папку Drive) | **Notion** | Notion | Claude Code |
| Голос бренда, бриф, стратегия, оверрайды (`voice/context/strategy/overrides`) | **git (`projects/{ID}/`)** | git | Claude Code (по диктовке оператора) |
| Ноу-хау агентства (`agents/`, `global/rules`, `standards`, шаблоны) | **git** | git | разработчик/оператор |
| Медиа: посты, картинки, видео, PDF, бренд-ассеты | **Google Drive** | Drive | Claude Code + человек может докинуть |
| Архив сессий (`logs/claude-code/...`) | **S3 (Timeweb)** | S3 | `upload-session.mjs` |

Ключевое следствие: **операционная роль `content-plan.md` / `.html` / `.pdf` уходит** —
её заменяют строки-задачи в Notion. Файлы голоса/брифа/стратегии остаются в git как
была. Деление естественное: Notion держит текст/статусы/структуру, Drive — бинарь,
Notion сам по себе не медиа-хранилище.

## Компонент 1 — Google Drive (медиа-слой, заменяет S3)

### Что делаем
- Новый тул `tools/gdrive.mjs` по образцу `tools/s3.mjs`: команды
  `list / put / get / rm / sync-up / sync-down / url / exists` **+ новое `share`**
  (выдать клиенту доступ / получить публичную ссылку на папку или файл).
- Рендер-пайплайн (`render-html.js`, `slides-to-pdf.js` и пр.) рендерит во временный
  `/tmp/...`, затем `gdrive.mjs put` в папку клиента — как раньше с S3.
- Перевести потребителей S3-медиа на Drive, обновить `docs/s3.md` (или новый
  `docs/gdrive.md`) и упоминания S3 в `agents/*` и `global/rules.md`.

### Структура папок Drive
```
bit&pix/  (корень, Shared Drive)
  {ClientName}/
    posts/{YYYY-MM-DD}-{N}/     рендеры слайдов, картинки, финальный PDF поста
    assets/                     бренд-ассеты клиента, исходники
```
Каждая строка-пост в Notion ссылается на свою папку `posts/{дата}-{N}/` в Drive.

### Креды и важный технический нюанс
- Google Cloud проект → включить Drive API → **service-account JSON** в `.env`
  (gitignored), `npm i googleapis`.
- ⚠️ **Service-account не владеет файлами в обычном My Drive (нулевая квота).**
  Решение — **Shared Drive** (бывш. Team Drive) воркспейса bit&pix, где service-account
  добавлен участником с правом записи. Тогда и программная заливка работает, и человек
  может зайти и докинуть файл в ту же папку. Это закладывается в дизайн с самого начала.

### Что заменяет
`tools/s3.mjs` (для медиа), медиа-ветки в `upload-session.mjs` оставляем на S3 (см. ниже),
`docs/s3.md` → переписать под Drive, `.gitignore` медиа-правила без изменений.

## Компонент 2 — Notion (операционный CRM)

### Подключение
- **Официальный Notion MCP-коннектор** (hosted, OAuth), не кастомный тул: доску я веду
  интерактивно, MCP даёт полный CRUD с нулём кода для поддержки. Кастомные Notion-скрипты
  добавим позже, только если появится автоматизация (напр. публикация).
- Завести Notion MCP как MCP-сервер (он **не** предподключён, в отличие от
  Google-коннекторов claude.ai): добавить сервер `https://mcp.notion.com`, пройти OAuth,
  расшарить integration в нужное рабочее пространство/базы.

### Схема баз
**База «Клиенты» (тонкая карточка):**
- Name (title)
- Platform(s) (multi-select: VK / MAX / Instagram / Telegram / …)
- Current focus (text)
- Drive folder (url → папка клиента)
- Local project ID (text → совпадает с `projects/{ID}`)
- Status (select: active / paused)
- Operator (person/text, опционально)

**База «Посты» (задачи-посты, заменяет `content-plan`):**
- Title (title)
- Client (relation → Клиенты)
- Date / Deadline (date)
- Platform (select)
- Status (select: `черновик` / `ждём материалы` / `на согласовании` / `готово` /
  `опубликовано` — переиспользуем существующую таксономию из `CLAUDE.md`)
- Rubric (select — из рубрикатора `strategy.md` проекта)
- Format (select: Reel / Карусель / Фото / Текст)
- Assets (url → папка поста в Drive)
- Notes / feedback (text)
- Owner (person/text, опционально)

### Что я делаю в Notion
Полный CRUD: смотрю «что на каком статусе / что в следующем» (приходит менеджер —
отвечаю по доске), создаю строки из сгенерированного контент-плана, двигаю статусы по
ходу работы, правлю/удаляю задачи, веду карточки клиентов.

## Компонент 3 — База знаний (остаётся локально)

- `projects/{ID}/{context,voice,strategy,overrides}.md` — **остаются в git**. Я читаю их
  в начале каждой задачи (быстро, версионируется, лучше «помню»). Оператор диктует
  правку голосом → я правлю файл.
- `agents/`, `global/rules.md`, `global/standards.md`, `global/templates/`, `skills/` —
  без изменений, остаются в git.
- Если позже менеджеру понадобится читать брифы в Notion — добьём точечное read-only
  зеркало (Вариант C), это малая надстройка над А. **Сейчас не делаем (YAGNI).**

## Компонент 4 — SOP онбординга нового клиента

Новый док (напр. `docs/client-onboarding.md`): пошаговая процедура заведения клиента,
трогает все три места.

1. **Бриф-диалог** — существующая экспертиза `brief`: собрать инфу по клиенту.
2. **Локально:** создать `projects/{ID}/` из `projects/_template/`, заполнить
   `context / voice / strategy / overrides`.
3. **Drive:** создать папку клиента `bit&pix/{ClientName}/` со структурой
   `posts/` + `assets/`, при необходимости выдать клиенту доступ (`gdrive.mjs share`).
4. **Notion:** создать карточку в базе «Клиенты» (платформа, фокус, ссылка на папку
   Drive, local project ID), затем строки-задачи в базе «Посты» из контент-плана.
5. **Порядок и ответственность:** кто что делает руками, что делает Claude Code.

Док пишется **последним** — ссылается на структуру Drive и схему Notion.

## Что остаётся на S3 (без изменений)

Архив сессий `logs/claude-code/by-project | by-date | _index`, который пишет
`upload-session.mjs`. Это машинный архив для майнинга паттернов — человек туда глазами
не лезет, уже работает presigned-url + read-modify-write индекс. На Drive не переносим
(лишняя возня без выгоды). `tools/s3.mjs` остаётся ради логов.

## План реализации (фазы, каждая — отдельный цикл)

1. **Фаза 1 — Drive медиа-слой.** `tools/gdrive.mjs` + Shared Drive + креды + перевод
   рендер-пайплайна и потребителей медиа с S3 на Drive + переписать `docs/s3.md`.
   Начинаем с неё: механическая, разблокирует правильное хранение файлов.
2. **Фаза 2 — Notion CRM.** Подключить Notion MCP, создать базы «Клиенты»/«Посты» по
   схеме, перенести операционку текущих проектов из `content-plan.md` в Notion, ретайр
   операционной роли `content-plan.*`.
3. **Фаза 3 — SOP онбординга.** `docs/client-onboarding.md` поверх готовых Drive + Notion.

После каждой фазы — запись в `global/UPDATES.md`.

## Вне scope / YAGNI

- Кастомные Notion-скрипты (только MCP, пока нет автоматизации публикации).
- Зеркало знаний в Notion (Вариант C) — только если менеджер реально попросит.
- Перенос логов сессий на Drive.
- Автопубликация в соцсети — отдельный человек/расписание, не этот дизайн.
- Клиентский PDF контент-плана как экспорт из Notion — только если понадобится.
