## Цель

Начальник описал видение «одно окно»: специалист тянет 20–30 проектов, ИИ снимает
~80% рутины, **финальную публикацию всегда жмёт человек**. Приземляем это не в одно
кастомное приложение, а в **3 окна + Notion-БД за ними** — на готовых инструментах,
склеенных через Claude Code.

## Архитектура: 3 окна + Notion

```
Окно 1 — Чаты (Chatwoot)      клиентские диалоги, омниканал TG/VK/MAX. Развёрнут.
Окно 2 — Claude Code (я)      ОСНОВНОЙ рабочий экран: подсказываю что следующим,
                              вместе с оператором делаем пост, пушу в Postiz, веду Notion.
Окно 3 — Postiz (КАНДИДАТ)    превью перед публикацией: специалист ок/не ок → публикация.
                              На сервере, допиливается. НЕ финальное решение — может
                              замениться другим инструментом публикации.

Notion (за окнами)            БД / источник истины операционки + Kanban для начальника.
                              Веду я; начальник смотрит/иногда правит; рядовой оператор
                              руками почти не лезет.
S3 (Timeweb)                  медиа под префиксом smm/ (Google Drive отменён, см. Компонент 2)
                              + архив сессий Claude Code (logs/claude-code/…).
```

Развилка «Notion как пульт vs кастомное окно» закрыта: **мульти-тул, Notion остаётся**
как БД/доска (не главный экран оператора). Публикация = Postiz, диалоги = Chatwoot —
кастомного приложения не строим.

## Модель данных (Вариант А)

> **Источник истины операционки → Notion. Знания, что я читаю в начале задачи →
> локально (git). Бинарь → S3 (префикс `smm/`). Под публикацию → копия в Postiz. Архив сессий → S3.**

| Данные | Где источник истины | Кто правит |
|--------|---------------------|------------|
| Посты-задачи, статусы, очередь, приоритет (Kanban) | **Notion** | Claude Code (я), начальник иногда |
| Тонкая карточка клиента (платформа, фокус, ссылка на медиа S3) | **Notion** | Claude Code |
| «Личное дело» проекта: голос, бриф, стратегия, оверрайды, «запомни/не делай» | **git (`projects/{ID}/`)** | Claude Code по диктовке оператора |
| Общие правила на все проекты (тире, точки после смайлов и т.п.) | **git (`global/rules.md`)** | оператор напрямую |
| Ноу-хау агентства (`agents/`, `standards`, шаблоны) | **git** | разработчик/оператор |
| Медиа: посты, картинки, видео, PDF, ассеты | **S3** (бакет `seo`, префикс `smm/`) | Claude Code; человек — через Cyberduck |
| Пост под публикацию (текст + медиа, расписание) | **Postiz** (копия из S3) | Claude Code пушит, человек публикует |
| Архив сессий (`logs/claude-code/...`) | **S3** | `upload-session.mjs` |

Операционная роль `content-plan.md` / `.html` / `.pdf` **уходит** — её заменяет
Kanban постов в Notion.

## Компонент 1 — Notion (источник истины операционки + доска начальника)

### Подключение
- **Notion MCP-сервер на Internal Integration Secret** (`NOTION_TOKEN` в `.env`, уже
  записан 13.06.2026). Токен, а не OAuth — один секрет раздаётся команде. Локальный
  Notion MCP-сервер настраивается на этот токен (команда запуска — деталь реализации).
- Доступ строго к расшаренным через «Connections» страницам/базам. Завести интеграцию
  и расшарить — по `docs/access-setup.md`.

### Схема баз и связи

```
Клиенты ──< Планы ──< Посты
 (клиент)    (месяц)   (карточка = пост)
```
Пост знает и свой план, и своего клиента. План катит к клиенту на согласование;
посты делаются после утверждения плана.

**База «Клиенты» (тонкая карточка):**
Name · Платформы (VK/Instagram/MAX/Telegram) · Текущий фокус · Папка Drive (url) ·
Local project ID · Статус (active/paused) · Оператор.

**База «Планы» (контент-план = клиент × период):**
Name · Клиент (relation) · Период (месяц/даты) · Статус (`черновик` → `на согласовании
у клиента` → `утверждён` → `в работе` → `закрыт`) · PDF (url → Drive, снапшот для
клиента) · Заметки/ОС.

> Источник истины плана — строки Notion. То, что видит клиент, — **сгенерированный
> снапшот** (PDF/визуал из `html→pdf` пайплайна) в Drive, отправляется через Chatwoot.
> Это и есть «ретайр операционной роли `content-plan.md`»: ведём в Notion, клиенту
> отдаём снапшот. **Два уровня согласования:** план целиком → затем каждый готовый пост.

**База «Посты» (Kanban, карточка = пост):**
Title · Клиент (relation) · **План (relation)** · Дедлайн · Платформа · Статус
(`черновик` / `ждём материалы` / `на согласовании` / `готово` / `опубликовано`) ·
Рубрика · Формат (Reel/Карусель/Фото/Текст) · Ассеты (url → Drive) · Ссылка на
публикацию · Приоритет · Заметки/ОС · Ответственный.

`Приоритет` отражает правило начальника: **срок** + **объём материалов от заказчика и
ожидаемое время ответа** (материалы запрашивать заранее). Срочный пост «вне плана» от
клиента создаётся и цепляется к текущему плану.

### Что я делаю
Полный CRUD: создаю строки из контент-плана, двигаю статусы по ходу, читаю доску для
приоритизации («что следующим»), веду карточки клиентов. Начальник видит тот же Kanban
и при желании правит.

## Компонент 2 — Медиа (S3 Timeweb — остаёмся; Drive отменён)

> 🔄 **Решение 14.06.2026:** переезд медиа на Google Drive **отменён** (после ресёрча).
> Причины: сервис-аккаунты после 15.04.2025 не пишут в личный My Drive; Workspace+Shared
> Drive не оплатить из РФ (санкции); личный Drive через OAuth — хрупко и привязано к одному
> аккаунту. S3 уже работает, RU-родной, дёшев, headless-надёжен, team-safe.

### Как есть
- Медиа — в **S3** (бакет `seo`), всё под префиксом `smm/`:
  `smm/projects/{ProjectID}/posts/{дата}-{N}/`, `smm/projects/{ProjectID}/assets/`.
  Тул — `tools/s3.mjs` (без изменений). Гайд — `docs/s3.md`.
- Рендер во `/tmp` → `s3.mjs sync-up` под `smm/…` → чистим `/tmp`.
- Строка-пост в Notion ссылается на S3-ключ/папку в поле «Ассеты».

### Просмотр человеком (вместо Drive-UI)
- директору — **Cyberduck**/S3 Browser (бакет как папка, drag-and-drop) или веб-панель Timeweb;
- клиентам — **presigned-ссылки** (`node tools/s3.mjs url <ключ>`), уже работает.

Google service-account ключ от директора — **не нужен** (путь отменён).

## Компонент 3 — Публикация и превью (кандидат: Postiz)

> ⚠️ Инструмент публикации **не финализирован**. Postiz — текущий кандидат (стоит на
> сервере, допиливается), но может замениться. Поэтому изолируем его за тонким
> адаптером `tools/publish.mjs`, чтобы смена инструмента не растекалась по системе.

- Готовый пост (текст + медиа из Drive) я пушу в **Postiz через API** как черновик/
  запланированный → специалист открывает Postiz, смотрит превью под соцсеть → **ок/не ок**
  → решает публиковать сейчас / в отложку / по времени. **Финальную кнопку жмёт человек.**
- Notion-строка получает ссылку/id поста в Postiz и статус `на согласовании`→`готово`→
  `опубликовано`.
- Реализация: `tools/postiz.mjs` (или MCP) поверх Postiz API; креды/endpoint в `.env`.
- ⚠️ **Открытый вопрос:** Postiz из коробки покрывает не все 4 сети — Instagram/Telegram
  обычно да, **VK и MAX** под вопросом. Уточнить, что именно допиливается; для
  непокрытых сетей публикация может идти иначе.

## Компонент 4 — База знаний и память (локально, Вариант А)

  внутренний «сухой» файл (U1/U2): тональность, проект, ЦА, конкуренты, рубрики,
  воронка; заказчику не показываем, ему уходит контент-план. `Convium_SMM.pdf` —
  референс-эталон структуры (распарсить нечем — разработчику сохранить как образец).
- **«Личное дело» / память паттернов (2 уровня, из интервью C):**
  - **Проектный** — индивидуальные «запомни это / так не делай» в `overrides.md`.
  - **Глобальный** — общие правила в `global/rules.md`, оператор пишет напрямую.
  - Цель: повторяющийся паттерн в ОС обнаружить, запомнить (в идеале с первого раза),
    больше не повторять. Механизм активного майнинга — отдельный трек (см. отложенное).
- Бриф = `agents/brief/questions.md` (33 вопроса, Q33 — мастер-вопрос от Максима,
  высший приоритет). Этого достаточно для старта проекта.
