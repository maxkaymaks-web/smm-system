# Онбординг процесса — интервью с начальником

Этот документ — **заготовка под описание процесса работы**. Система переходит
на новую модель (оператор ведёт много проектов, Claude Code — сильный помощник),
и нужно зафиксировать, как этот процесс должен работать на самом деле, со слов
человека, который им руководит.

---

## Для начальника

Привет. Чтобы запустить новую модель, нам нужно от тебя одно: **рассказать, как
всё должно работать**. Реализацией займётся разработчик — тебе ничего не нужно
делать руками, только описать.

Как это происходит:

1. Запусти Claude Code в этом репозитории (`claude`) и напиши: **«Я начальник,
   готов описать процесс»**.
2. Агент вывалит тебе **один большой блок открытых вопросов** (он ниже, в разделе
   «Блок вопросов»). Без вариантов ответа, без тестов — просто список тем.
3. **Включи голосовой ввод и надиктуй всё, что можешь**, по порядку или вразнобой —
   как удобно. Не структурируй, не вылизывай: агент сам разложит по полочкам.
4. Агент **только записывает** твои слова в этот документ (раздел «Ответы»),
   ничего не реализует и не лезет с уточнениями по мелочи. Если что-то совсем
   непонятно — задаст короткий вопрос, не больше.
5. Когда выговорился — скажи **«Закончил»**. Агент сохранит и закоммитит.
6. Дальше приходит разработчик и по твоим ответам строит систему.

Чем подробнее расскажешь — тем меньше потом переделок. Не знаешь ответа на
какой-то вопрос — так и скажи «не знаю / решим позже», пропускаем.

### Параллельно — выдать доступы (можно до или после интервью)

Чтобы Claude Code мог работать с Google Drive и Notion, нужно один раз завести
креды. Процедура — в **`docs/access-setup.md`**: создать service-account Google
(ключ + доступ к рабочей папке) и Notion-интеграцию (Internal Integration Secret +
расшарить нужные страницы). Заполни её и **пришли получившиеся креды разработчику** —
он реализует интеграцию и протестирует на этих кредах. Операторам креды раздаются
позже, когда интеграция готова (это сделает разработчик).

## Для агента (Claude Code), когда пользователь говорит «я начальник»

**Твоя роль — интервьюер-стенографист, не исполнитель.**

- Выведи начальнику **весь блок вопросов разом** (раздел ниже). Не по одному.
- Дай ему надиктовать. **Ничего не реализуй**: не трогай код, не создавай файлы,
  не предлагай решения, не правь архитектуру.
- Записывай ответы в раздел **«Ответы начальника»** этого файла — структурируй
  надиктованное по темам вопросов, но **не выкидывай детали и формулировки**.
  Сохраняй его слова, не пересказывай в свою сторону.
- Уточняющие вопросы — только если без них ответ буквально нечитаем. Максимум
  пара коротких, не грузить.
- Когда начальник говорит «закончил» — сохрани файл, покажи краткое содержание
  записанного для проверки, и закоммить: `docs: процесс от начальника — интервью`.
- **Не финализируй за разработчика.** Реализация (Notion, Google Drive, рерайт
  агентов, логирование) — не в этой сессии и не тобой.

### G. Что убрать / что оставить

21. Что наоборот работает хорошо и должно остаться?

### H. Доступы и безопасность

**Главная цель / бизнес-модель.**
Сделать SMM для малого и среднего бизнеса доступнее и дешевле. Механика: строим
очень удобную и автоматизированную систему, в которой работает живой
SMM-специалист. Система забирает на себя бóльшую часть рутины (условно до 80%),
поэтому специалист может вести кратно больше проектов. За счёт количества проектов
снижаем стоимость услуги для клиента.

**Полный фронт работ SMM-специалиста (как у реального человека):**
1. Разработать стратегию, забрифовать клиента.
2. Разработать контент-план.
3. Согласовать контент-план с заказчиком.
4. Работать по контент-плану — создавать посты.
5. Скидывать посты на согласование.
6. Учитывать правки.
7. Проводить финальные корректировки и публиковать в соцсети.
8. Проводить аналитику, анализировать её, сводить в отчёты, скидывать клиенту.

**Концепция «одного окна» (пульт управления).**
Чтобы специалист мог брать больше проектов, всю его работу нужно свести в одно
окно — единый интерфейс, где бóльшую часть работы делает нейросеть:
- Бриф клиента, анализ, формирование целей, формирование воронки — нейросетью, но
  **на основе реальной документации, реальных боевых фреймворков и методов**, а не
  галлюцинаций. Нейросеть должна быть обучена на реальных знаниях и работать «как
  по ним».
- Разработка контент-плана и постов — уже реализовано: нейросеть умеет писать
  тексты, делать дизайны через HTML + генерацию картинок через fal.ai.
- В этом же окне — диалоги с заказчиками (общение).
- В этом же окне — предпросмотр постов: видно, как пост будет выглядеть в
  конкретной соцсети, без захода в репозиторий или на диск.
- Система сама отсылает посты на согласование.
- Минимум переключений между окнами. Все проекты видны в одном окне как пульт
  управления.
- Специалисту остаётся: мелкие корректировки → кнопка «отправить» / «опубликовать».
- Система сама публикует в соцсети.
- Статистику тоже смотреть из этого же окна.

**Масштаб и боль.**
Цель — чтобы специалисту было комфортно вести 20–30 проектов одновременно, чтобы
«не кипели мозги». Сейчас даже с уже разработанной системой (которая умеет делать
посты по команде/пушу) большой ресурс уходит на: общение, корректировки, учёт
специфических особенностей каждого проекта (что заказчику нравится/не нравится, где
нужно участие). Это при написании промта сильно сжигает умственный ресурс.
Сейчас держали ~5 проектов в голове — уже возникали сложности, можно было
запутаться, что-то шло не туда.

**Что автоматизировать (через реальные решения — боты и т.п.):**
отложенный постинг, аналитику, учёт специфик, отправку клиенту, получение обратной
связи. Специалист работает «под капотом» над качеством и принимает финальные
решения о публикации.

**Жёсткое правило.**
Нейросеть сама ничего не решает по публикации. Финальное решение о публикации —
всегда за человеком. Человек присутствует на валидации качества.

**Зоны ответственности для интервью.**
Начальник отвечает за маркетинг и сам может выступать как SMM-специалист — ему
можно задавать вопросы про то, какие работы можно автоматизировать, а какие нет.
Технические вопросы — к разработчику, не к начальнику.

### A. Стратегия и бриф

**Что отдаём системе, что — человеку (#3).**
Системе можно полностью отдать построение контентной воронки по классическим
устоявшимся моделям (AIDA; TOFU/MOFU/BOFU и др. — таких воронок в маркетинге
много, использовать реальные). Система сама придумывает рубрики и выстраивает
**процентное соотношение рубрик** так, чтобы складывалась воронка: вовлечение →
интерес → доверие → покупка. **Человек один раз согласовывает** рубрики и воронку.

**Что ОБЯЗАТЕЛЬНО проговаривать с человеком (#3).**
Всё, что касается **аудитории, тональности и прочей чувствительной информации** —
обязательно проговаривается с человеком, система не решает это сама.

**Бриф (#2, файл).** Набора из `agents/brief/questions.md` достаточно для старта.
Мастер-вопрос Q33 — высший приоритет по поведению/алгоритму проекта.

### B. Личное дело проекта — учёт специфики клиента (главная боль)

**Природа специфики (#4).** Большинство заказчиков в малом/среднем бизнесе
действуют **не от маркетинговых знаний, а от «нравится / не нравится»** — вплоть
до конкретных слов, смайликов, фраз, «полной херни». Это нужно держать в голове,
чтобы заказчик остался и продолжил работать. Касается не только текста, но и
дизайна: какие-то цвета, визуальные элементы должны быть учтены.

**Личное дело (#4).** По каждому проекту должно быть **личное дело с контекстом**,
куда записываются все «запомни это / так больше не делай». Это учитывается в работе
над контентом и дизайном.

**Работа с «кривой» ОС (#4).** Заказчики часто некомпетентны как клиенты
агентства и пишут невнятно. ОС нужно уметь: запоминать, иногда **переводить/
интерпретировать**, задавать уточняющие вопросы, чтобы заказчик расписал понятнее,
что делать / не делать. Очень тонкий момент, требует грамотной работы.

**Откуда набирается специфика (#5).** Из первичного брифа + из обратной связи на
посты / контент-план / аналитику + просто из того, что заказчик пишет. Система
работает **не только по контент-плану, но и в пассивно-активном режиме**: заказчик
может написать «у нас что-то произошло / появилась идея, хочу такой пост, желательно
срочно» → это **принудительно добавляется в контент-план** и отрабатывается
системой + специалистом. В таких задачах тоже копится специфика («люблю, чтобы
было написано вот так») — у каждого проекта индивидуальная.

### C. Паттерны в обратной связи (память системы) (#6)

Система должна **обнаруживать повторяющиеся паттерны** в ОС. Пример: в одном посте
заказчик попросил «уберите вот это», в другом — то же самое. Это паттерн — его надо
**обнаружить, запомнить и больше никогда не делать**. Идеально — запоминать с
первого раза. Особенно важна оперативная реакция, когда клиент начинает
раздражаться («я же это уже повторял») — такое больше не должно повторяться.

**Два уровня правил:**
- **Только для одного проекта** — индивидуальные пожелания клиента.
- **Для всех проектов сразу** — общие правила (пример: вместо длинных тире — короткие;
  после смайликов не ставить точки). Эти правила может вписывать **сам SMM-специалист
  (оператор) напрямую в систему**, и они «зашиваются» в общий контекст для всех
  проектов.

### D. Согласование и работа с правками

**Как было раньше (#7, от этого хотим уйти).** Claude формировал контент-план в PDF
по контексту/стратегии → специалист **руками** выкачивал PDF, скидывал заказчику,
ловил ОС, передавал обратно Claude. Вся коммуникационная рутина — руками специалиста.

**Мутные правки (#8).** Заказчик может дать ОС вида «нет, не нравится, переделай»
без конкретики (это и есть «мутная правка»), может надиктовать голосовое. Система,
получив ОС, должна **определить, достаточно ли информации — не фантазируя и не
додумывая за заказчика**. Если недостаточно — задаёт уточняющие вопросы и **не
прекращает**, пока не соберёт всю нужную информацию; только тогда передаёт ОС
специалисту в проработку.

**Круги правок (#9, не идеал — надо улучшать).** Сейчас: система отдаёт пост
специалисту → специалист на этапе системы дорабатывает обычно в 2 (иногда 3) круга
(визуал, текст, понимание проекта/контекста) → потом скидывается заказчику → от него
ещё 1–2 круга. Итого ~5–6 кругов. **Цель — свести к ≤3 кругам**, и чтобы круги были
только со стороны заказчика, а на этапе системы всё было сделано идеально (специалисту
не надо доделывать мелочи за системой).

### E. Каналы общения и работа в переписке

**Каналы (#10).** Самый частый — **Telegram**; отдельно **ВКонтакте**; немного, но
есть **MAX** (новый российский мессенджер). В идеале — **свести все диалоги в одно
окно**, т.к. переключение между каналами — большой cost по вниманию/времени.

**Что система делает в переписке (#11).** Уметь: скидывать материалы на
согласование; забирать ОС; при нехватке информации — задавать уточняющие вопросы;
если заказчик пишет первым и просит пост/задачу — давать дежурные ответы («спасибо,
передал в работу»). Плюс **предлагать заготовленные ответы**: на входящее сообщение
система предлагает свой вариант ответа, специалист либо соглашается, либо редактирует —
так он тратит меньше времени на коммуникацию.

### F. Публикация

**Соцсети (#12).** На первое время нужны ровно четыре: **ВКонтакте, Instagram, MAX,
Telegram**. Больше пока не нужно.

**Финальная кнопка — только за человеком (#13).** Пост уходит на согласование →
заказчик одобряет → пост **всё равно возвращается к специалисту**, подсвечивается
«согласовано, можно публиковать» → специалист решает: публиковать сейчас / в
отложку / по времени, которое предлагает система (нажать одну кнопку). Специалисту —
право последней кнопки + возможность внести корректировки даже на этом этапе (так
бывает часто).

### G. Грань «человек / нейросеть» по этапам (#14, #15)

1. **Бриф + интерпретация брифа → стратегия/воронка** — человек ОБЯЗАН участвовать.
   Система предлагает вариант (как строить стратегию/воронку), **человек смотрит и
   даёт ОК / корректировку**. Здесь нельзя ошибаться — это стратегические решения,
   влияющие на всю дальнейшую работу и результат.
2. **Разработка контент-плана + скидывание заказчику + сбор ОС** — можно полностью
   отдать системе.
3. **Работа над постом по контент-плану.** Бывают посты, которые система делает
   полностью сама. Бывают посты, требующие материалов (фото/видео/знания) — система
   **сама заранее пишет заказчику в личку**: «к такой-то дате нужны такие-то
   материалы». Дальше собирает пост (генерит материалы / берёт присланные / пишет
   текст). **На готовом посте подключается человек** — смотрит, вносит корректировки
   либо говорит «ОК, отправляй на согласование».
4. **После согласования заказчиком** (ОС внесена, повторно согласовано) пост
   возвращается человеку → **финальное решение о публикации**. Без разрешения
   человека публикации нет — во избежание дурацких ошибок.
5. Дальше циклически по всем постам.
6. **Аналитика** — система собирает статистику еженедельно/ежемесячно по основным
   метрикам, отдаёт специалисту, при необходимости делится с заказчиком (можно
   красивой формой — PDF-отчёт).

**Чему нейросети нельзя доверять (#15).** **Проработка целевой аудитории** — здесь
нейросеть сильно выдумывает и врёт. Нужны **реальные данные: интервью, реальные
действия**. Если ниша понятная/обширная и общеизвестная — можно взять данные из
интернета или теоретически предположить. **На сложных нишах фантазировать про ЦА
запрещено** — нейросеть не понимает, что это за аудитория, ни в каких случаях это
не получалось.

### H. Контроль качества

**Что проверяю в первую очередь (#16).** 1) Фирменный стиль и тональность; 2)
соответствие целевой аудитории — её болям и триггерам, фреймворку JTBD (как в
эталонной стратегии Convium); соответствие намеченной стратегии. Затем — **визуал
по брендбуку** (шрифты, визуальные косяки, охранные поля, чистота, воздух). Затем —
**опечатки, форматирование текста** (деление на абзацы, смайлики, работа со списками/
нумерацией), чтобы пост выглядел привлекательно.

**Где чаще всего брак (#17, чек-лист «обязательно проверять»).**
- Текст система пишет более-менее хорошо — **основная боль в ДИЗАЙНЕ**.
- Нейросеть **не всегда берёт нужные шрифты и дизайн-систему заказчика** — большой
  косяк, который сама не видит.
- Дизайн-косяки: текст съехал / наехал / элементы друг на друга / слишком близко к
  краю; либо наоборот — слишком пусто, много пустого пространства, нет объектов,
  скучный фон, нет текстуры, нет доп. генераций картинок для разнообразия → пост
  получается пресным и неинтересным. **Это самая боль.**
- По тексту подробный чек-лист не нужен — явные текстовые паттерны (как писать / как
  не писать) вырабатываются со специалистом после пары пробных постов.

### I. Аналитика и отчёты

**Метрики (#18).** Основные: подписчики, **прирост подписчиков**, охват, количество
контента, **вовлечённость (ER, %)** = (реакции + комментарии + репосты и т.п.) /
число подписчиков. Бизнес-конверсии (покупки, переходы) — в соцсетях сложно
отследить, **в отчёт не добавлять**; брать метрики, которые можно вытащить из самой
соцсети (по API / публичным данным).

**Частота и форма отчётов (#19).**
- **Специалисту:** еженедельно по каждому проекту + ежемесячно сводно по всем.
- **Управленцу (начальнику):** еженедельно по всем проектам и по работе специалиста
  с заказчиками.
- **Заказчику:** ежемесячно обязательно, в виде **PDF**. Еженедельно — опционально
  (дать выбор: еженедельно/ежемесячно).
- Специалисту и управленцу достаточно **дашборда в самой системе** (удобно
  переключаться по проектам, смотреть статистику/эффективность).
- **Пуши/алерты:** при аномалиях (плохих или, наоборот, очень хороших) — чтобы
  специалист/управленец мог оперативно отреагировать.

### J. Пульт управления (главный экран)

**Видение (#20).** Главный экран — сводка по всем проектам. Гипотеза начальника
(«честно не знаю, предполагаю»): большая **Kanban-доска**, куда складываются все
посты по всем проектам. **Карточка = один пост**; в карточке уже собраны все
сгенерированные материалы (тексты, визуалы) — специалисту достаточно проверить и
кинуть на согласование. Задачи на доске распределены по приоритетам: за что браться
сейчас, где проблема, где нужно решение специалиста, что висит на согласовании у
заказчика без ответа. Рядом, в другом окне — диалоги. Плюс пара KPI (общие нужные
цифры). По сути — **большая CRM по постам среди всех проектов и соцсетей**.

**Приоритизация (#21).** Два главных фактора (см. также уточнение U2 ниже):
1. **Срок** — чем быстрее нужен пост, тем выше приоритет.
2. **Объём запрашиваемых материалов + ожидаемое время ответа заказчика.** Посты,
   требующие материалов от заказчика, тоже в приоритете: заказчик не пришлёт день в
   день — может тянуть дни/недели, поэтому запрашивать **заранее**. Речь не только о
   фото/видео, но и о знаниях, которые есть только у заказчика (специфика товара,
   условия, промо, новости). Цель — чтобы к дате публикации материалы уже были.

### K. Бизнес-цель (зачем всё это)

Сделать SMM для МСБ доступнее/дешевле за счёт автоматизации ~80% рутины: один
специалист ведёт кратно больше проектов (цель — комфортно 20–30), цена для клиента
падает за счёт количества. Человек — на валидации качества и финальной публикации.

### Уточнения (заданы после рассказа, ответы 13.06.2026)

**U1. Глубина / объём стратегии.** Эталон Convium (100 стр.) — это **большой
проект**, где стратегию прорабатывали основательно под работу команды людей. Для
нашего формата её **смело сжимать до ключевых страниц**, с которыми работает
система. Для малого/среднего бизнеса достаточно **упрощённой стратегии**, где
описано: тональность, сам проект, **целевая аудитория (её можно расписать
поподробнее)**, конкуренты, контентная стратегия / рубрики, SMM-воронка (как люди
движутся). Главное помнить: **делаем контент не ради постов, а ради конкретного
бизнес-результата заказчика** — продажи/услуги/товары, либо имиджевый результат
(для блогеров и т.п. — подписчики/просмотры). Вся стратегия крутится вокруг этой
главной цели (польза заказчику). Стратегию можно «сушить».

**U2. Кому показываем стратегию.** Стратегия — **только внутренний файл**. Мы **не
продаём услугу разработки стратегии**, формируем её сами для своей работы. Первое,
что уходит заказчику на согласование, — **контент-план на месяц**, по которому
работаем. (Стратегию заказчику не показываем.)

**U3. Управленческий отчёт (что хочет видеть начальник).** Нужны **показатели
жизнеспособности продукта** — общая динамика по «жизненным» метрикам сервиса:
- как быстро отвечает SMM-специалист;
- средний круг правок на пост;
- сколько постов запланировано / сколько опубликовано;
- по каким проектам статистика хорошая, по каким плохая;
- где ошибки;
- настроение заказчика (где «добрый», где «злой»).
Смысл: это те показатели, **порча которых = продукт превращается в плохой и от него
уходят люди**. Нужны начальнику именно для поддержания качества сервиса.
